# Home Assistant Ring Face Recognition Project Constitution

**Project:** Local-First Residential Person Identification for Home Assistant
**Applies To:** Ring Front Door → Video Bridge → Frigate → Face Recognition → Home Assistant → Notification
**Primary Home Automation Host:** Home Assistant OS on Raspberry Pi 3
**Initial AI/Video Host:** Local Mac for proof-of-concept; dedicated compute for production

## Purpose

This constitution defines the non-negotiable engineering principles, architectural
boundaries, safety rules, privacy requirements, testing expectations, and change-control
standards for the Home Assistant Ring person and face recognition project.

All implementation decisions, specifications, code, automations, infrastructure changes, and
future feature additions MUST comply with this constitution.

The project exists to add useful local intelligence to the existing Home Assistant security
system without weakening reliability, privacy, or household safety.

## Project Goal

The system SHALL:

1. Detect a person at the Ring Front Door camera.
2. Attempt face recognition only after a person has been detected.
3. Match the face to an explicitly enrolled known identity when confidence is sufficient.
4. Map the known identity to a user-maintained relationship category:
   - Family
   - Friend
   - Neighbor
   - Other Known
5. Treat every uncertain or unmatched identity as `Unknown`.
6. Publish the result to Home Assistant.
7. Send a useful notification such as:
   - `Chandra detected at Front Door — Family`
   - `John detected at Front Door — Neighbor`
   - `Unknown person detected at Front Door`
8. Keep normal Home Assistant and Ring automations working even when the AI subsystem is
   unavailable.

The system SHALL NEVER infer whether a person is family, a friend, or a neighbor based on
appearance. Relationship classification comes only from an explicit user-maintained mapping.

## Core Principles

### I.1 — Home Assistant Remains the Control Plane
Home Assistant is the orchestration system for the house. The Raspberry Pi 3 SHALL continue
handling: automations, notifications, device state, household logic, dashboards, Ring event
handling, presence logic, and MQTT integration. Video AI processing SHALL NOT be moved onto
the Raspberry Pi 3.

Rule: no implementation may introduce a video or AI workload that materially degrades Home
Assistant reliability.

### I.2 — AI Workloads Run Separately
Frigate, video decoding, object detection, and face recognition MUST run on a separate
compute host. Approved development path: Phase 1 — Mac as a local proof-of-concept; Phase 2 —
a dedicated AI/video host for production. Production hardware MUST be selected only after the
proof-of-concept establishes CPU/GPU requirements, stream stability, model performance,
storage requirements, and recognition accuracy.

### I.3 — Local Processing Is Preferred
Face embeddings, face libraries, recognition results, and internal identity mappings SHOULD
remain on locally controlled infrastructure whenever practical. Cloud services SHALL NOT
become mandatory for the face-recognition decision path unless explicitly approved. Ring's
existing cloud dependency may remain where required by the Ring platform, but the recognition
layer itself SHOULD remain local.

### II.1 — Explicit Enrollment Only
A person may be identified by name only if that identity has been intentionally enrolled. The
system MUST NOT: guess a person's name, infer relationship from appearance, label unknown
people as known based on weak similarity, or silently add new identities.

### II.2 — Unknown Is the Safe Default (NON-NEGOTIABLE)
When confidence is insufficient, `result = Unknown`. A false `Unknown` is preferable to a
false identity match. Recognition thresholds MUST therefore favor precision over aggressive
matching.

### II.3 — Face Recognition Must Not Unlock the House (NON-NEGOTIABLE)
Face recognition alone SHALL NEVER be sufficient to: unlock exterior doors, open the garage,
disarm security systems, disable alarms, grant physical access, or execute safety-critical
actions. Face recognition may initially be used only for: notifications, event
classification, dashboard status, history, and non-critical informational automations. Any
future physical-access automation requires a separate security design and an explicit
amendment to this constitution.

### II.4 — Protect Credentials and Identity Data
Credentials, tokens, API secrets, Ring authentication data, MQTT passwords, and identity
databases MUST NOT be committed to Git. Secrets MUST be stored using appropriate
secret-management mechanisms such as Home Assistant secrets, environment variables, Docker
secrets, or protected local configuration files excluded from version control. The face
library MUST NOT be exposed through an unauthenticated network share or public service.

### II.5 — Minimize Retention
Video, snapshots, and face images SHOULD be retained only as long as required for debugging,
training, recognition validation, or explicitly desired security history. Retention duration
MUST be configurable. Temporary proof-of-concept files SHOULD NOT silently become permanent
archives.

### III.1 — Person Detection Comes First
The recognition pipeline SHALL follow: video → person detected? (no → stop identity
processing; yes →) usable face? (no → `Unknown`; yes →) face recognition. Face recognition
SHALL NOT run indiscriminately on every frame when a person is not present.

### III.2 — Identity and Relationship Are Separate Concepts
The recognition engine determines `recognized_name`. Home Assistant or a local mapping layer
determines `relationship_category` (e.g. Chandra → Family, John → Neighbor, Alex → Friend,
Vendor1 → Other Known). The mapping MUST be explicit and editable.

### III.3 — Preserve the Original Security Event
AI enrichment MUST supplement, not replace, the original Ring event. If recognition fails,
the system MUST still retain the basic security fact ("Person detected at Front Door"). AI
failure SHALL NEVER suppress a valid security event.

### IV.1 — AI Failure Must Not Break Home Assistant (NON-NEGOTIABLE)
If Frigate, Ring-MQTT, the AI host, face recognition, or the network path fails, Home
Assistant MUST continue supporting existing functions such as Ring doorbell notification,
Ring motion notification, other household automations, media controls, thermostat logic,
dashboards, and MQTT functions unrelated to the failed AI subsystem.

### IV.2 — Every External Dependency Needs a Failure State
The implementation MUST explicitly handle: Ring stream unavailable, Ring authentication
failure, MQTT unavailable, Frigate unavailable, face-recognition engine unavailable,
corrupted or missing face library, camera offline, stale event, AI host offline, and Home
Assistant restart. No dependency may fail silently.

### IV.3 — Do Not Treat Unknown Data as Real Data
`battery = unknown` MUST NOT become `battery = 0`. Likewise, "identity unavailable" MUST NOT
become "Unknown person" unless an actual person event occurred. Unavailable, unknown, stale,
and genuine zero values MUST remain distinct.

## Development & Testing Standards

### V.1 — Build Incrementally
The project SHALL be implemented in this order: (1) local container environment, (2) test
video source, (3) Frigate starts successfully, (4) person detection, (5) MQTT connectivity,
(6) Home Assistant event visibility, (7) Ring video bridge, (8) real Front Door stream, (9)
face recognition, (10) known/unknown validation, (11) relationship mapping, (12)
notifications, (13) production hardware, (14) additional cameras. Steps SHALL NOT be skipped
merely to reach the final UI faster.

### V.2 — One Camera First
Phase 1 SHALL use only the Ring Front Door. Other Ring cameras may be added only after the
Front Door pipeline is stable, observable, performant, and acceptably accurate.

### V.3 — Mac Is a Development Environment, Not an Assumed Production Host
Local Mac testing is intended to validate Docker, Frigate, MQTT, stream ingestion, Home
Assistant integration, person detection, architecture, configuration, and development
workflow. The project MUST first determine whether the Mac is Intel or Apple Silicon.
Hardware-specific AI acceleration and native face-recognition support MUST be verified before
relying on it. No documentation or implementation may assume CPU instruction-set
compatibility without checking it.

### V.4 — Tests Must Be Reproducible
Every major capability requires a repeatable test. Minimum test cases:
- **T01 — Stream Test**: Front Door/test RTSP stream opens reliably.
- **T02 — Person Detection**: a person entering frame generates a person event.
- **T03 — Non-Person Motion**: routine motion without a person does not generate an identity.
- **T04 — Known Person**: an enrolled person can be correctly identified under normal
  conditions.
- **T05 — Unknown Person**: an unenrolled person is classified as `Unknown`.
- **T06 — Weak Face**: partial, blurry, dark, or low-confidence faces are not forced into a
  known identity.
- **T07 — MQTT**: Frigate events reach the configured MQTT broker.
- **T08 — Home Assistant**: Home Assistant receives and exposes the event.
- **T09 — Notification**: the expected iPhone notification is delivered.
- **T10 — Failure Isolation**: stopping the AI host does not break existing Home Assistant
  automations.

### V.5 — Every Feature Requires Acceptance Criteria
A feature is not complete because a container started, code compiled, a UI appeared, or a
single successful event occurred. It is complete only when its acceptance criteria pass
consistently.

## Dependency Governance

### VI.1 — Minimize the Stack
The baseline stack is: Ring → Ring-MQTT / supported video bridge → go2rtc / RTSP → Frigate →
MQTT → Home Assistant → mobile notification. Additional services SHALL be introduced only
when they provide a clear required capability.

### VI.2 — Preferred Dependencies
Expected dependencies include: Home Assistant, Mosquitto MQTT, Docker, Frigate, FFmpeg,
go2rtc, Ring-MQTT (or another proven Ring video bridge), the Home Assistant Frigate
integration, and optionally VLC/ffplay for RTSP debugging. A separate face-recognition
service SHOULD NOT be added if native Frigate capability satisfies the requirement.

### VI.3 — Pin and Document Significant Dependencies
Production deployments SHOULD document application version, image/container version, model
version, configuration version, and important compatibility constraints. Upgrades affecting
Ring integration, Frigate, MQTT, video decoding, object detection, or face recognition MUST
be tested before production adoption.

## Observability

### VII.1 — Every Stage Must Be Debuggable
The system MUST make it possible to determine: did Ring generate an event; did the stream
reach the AI host; did Frigate see a person; was a face usable; was an identity matched; what
confidence was produced; what identity was published; did MQTT deliver it; did Home Assistant
receive it; was the notification sent.

### VII.2 — Use Logs Before Guessing
When behavior is incorrect, troubleshooting SHALL prioritize, in order: entity state, event
history, Frigate events, MQTT messages, container logs, Home Assistant logs, network tests.
Random configuration changes are prohibited as a debugging method.

## Home Assistant Automation Rules

### VIII.1 — Use Verified Entity IDs
Automations MUST be created only from entities verified to exist in the actual Home Assistant
instance. Currently verified examples: `event.front_door_ding`, `event.front_door_motion`,
`switch.front_door_motion_detection`, `notify.mobile_app_pk_world`,
`person.praveen_kumar_konathala`. No automation may be built from assumed or invented entity
IDs.

### VIII.2 — Event and Configuration Entities Must Not Be Confused
An entity representing a configuration setting (e.g. `switch.front_door_motion_detection`)
MUST NOT be treated as the actual motion event. The actual event source MUST be used (e.g.
`event.front_door_motion`). This distinction applies across the project.

### VIII.3 — Automations Must Control Notification Spam
Repeated camera events require cooldown, deduplication, event correlation, or equivalent rate
limiting. Security alerts MUST remain useful rather than becoming noise.

## Performance Standards

### IX.1 — Measure Before Scaling
Before adding another camera, measure CPU utilization, memory use, decoding load, detector
latency, recognition latency, network bandwidth, storage use, and event-to-notification
latency.

### IX.2 — Detection Resolution and Recognition Resolution Are Deliberate Choices
Higher resolution is not automatically better. Camera streams and AI models MUST be tuned for
useful face size, sufficient image quality, acceptable latency, and acceptable CPU/GPU usage.

## Change Control

### XI.1 — Requirements Before Implementation
Any material feature must answer: (1) what problem are we solving; (2) what is the expected
behavior; (3) what dependencies are required; (4) what can fail; (5) what is the fallback;
(6) how will we test it; (7) what is the acceptance criterion. Implementation SHOULD begin
only after these are sufficiently clear.

### XI.2 — Architecture Changes Require Explicit Review
The following are architectural changes: changing the AI host; replacing Frigate; replacing
MQTT; adding cloud face recognition; enabling automatic physical access; retaining biometric
data externally; processing all cameras continuously; exposing services to the public
Internet. These changes require explicit review against this constitution.

### XI.3 — Constitution Takes Precedence
When an implementation shortcut conflicts with this constitution, the constitution wins
unless formally amended.

## Definition of Done

The initial project is considered successful when all of the following are true:

- Front Door video reaches Frigate reliably.
- Frigate reliably detects a person.
- Home Assistant receives the detection event.
- At least one intentionally enrolled person can be recognized under normal conditions.
- An unenrolled person produces `Unknown`.
- Low-confidence cases fall back to `Unknown`.
- Relationship mapping is explicit and editable.
- iPhone notifications identify the known person/category or report `Unknown`.
- Existing Ring doorbell and motion automations continue functioning.
- The Raspberry Pi 3 remains responsive.
- The AI service can be stopped without breaking the rest of Home Assistant.
- Credentials and face data are protected.
- Test results are documented.
- The system can later be expanded to another camera without redesigning the architecture.

## Governance

This constitution supersedes other project practices and guidance where they conflict, and
becomes the governing baseline for the project upon adoption.

**Versioning** uses semantic-style governance:
- **PATCH** — clarification with no policy change.
- **MINOR** — new principle or expanded requirement.
- **MAJOR** — removal or reversal of a core architectural/safety principle.

**Amendment requirements** — every amendment must document: (1) reason for change, (2)
affected principles, (3) architectural impact, (4) security/privacy impact, (5) testing
impact, (6) migration requirements. Amendments must also propagate to
`.specify/templates/*` and `CLAUDE.md` wherever they reference the changed principle.

**Compliance review** — `/speckit-plan`'s Constitution Check gate MUST be evaluated against
the Core Principles above before implementation proceeds; any violation MUST be justified in
that plan's Complexity Tracking section or the plan MUST be revised to comply. Use
`CLAUDE.md` for day-to-day runtime development guidance — this constitution governs the
non-negotiable, project-wide principles that guidance must not contradict.
